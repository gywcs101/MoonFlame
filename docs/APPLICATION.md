## 二、项目简介

MoonFlame 用**纯 MoonBit** 实现性能剖析的「最后一公里」：读取折叠栈（folded stack）文本，
聚合成调用树，计算每个函数的自身耗时与累计耗时，最终输出一张**自带交互功能的静态 SVG 火焰图**。

产出的 SVG 是**单个文件**：不需要 Go、Node 或任何运行时，双击即看，可直接贴进 README、
设计文档或复盘报告，也可归档进 CI 产物做版本间对比。

**项目边界很明确：它不做采样。** 采样与格式归一由上游工具完成（`moon-pprof`、`perf`、
`py-spy`、`async-profiler` 等），MoonFlame 专注于把这些工具产出的数据变成人一眼能看懂的图。
这条边界让项目保持专注，也让它的输入格式天然跨语言、跨平台。

## 三、项目方向与通用性

### 3.1 格式通用性

输入采用折叠栈这一**跨语言中间格式**（Brendan Gregg 定义）：

```text
____moonbit__main;moonflame::demo::bench__sorting;bubble__sort;array::Array::at 73382500
```

Linux `perf`、`py-spy`（raw）、`async-profiler`（collapsed）、`moon-pprof`（`pprof2folded`）
都能产出它。因此本工具**不绑定任何语言、平台或工具链**——这也是它作为「基础设施」的价值所在。

### 3.2 运行通用性

- **核心库零第三方依赖**：根包只做纯计算，不碰文件系统、时间或随机数；
- 文件 IO 被隔离在唯一的入口包 `cmd/main`，核心逻辑因此可在没有文件系统的环境里复用；
- 代码可编译到 `wasm` / `wasm-gc` / `js` / `native` 多个后端；
- 既可当命令行工具用，也可作为库被其他工具调用。

### 3.3 生态位置

现有的火焰图可视化方案都需要额外条件：

| 方案 | 门槛 |
| --- | --- |
| `go tool pprof` | 需要 Go 工具链与 `-http` 本地服务 |
| speedscope | 需要联网打开 Web 应用并上传文件 |
| Firefox Profiler | 需要浏览器会话 |

MoonFlame 补的是「**单文件、零环境、可归档**」这一空缺。

### 4.2 完整的渲染管线

| 模块 | 职责 |
| --- | --- |
| `folded.mbt` | 折叠栈解析：逐行处理，容忍超长单行（实测 181K 字符）与空帧名 |
| `calltree.mbt` | 调用树聚合、自身/累计耗时、**限深合并**、差异标注 |
| `layout.mbt` | 按值比例切分矩形，支持火焰图 / 冰柱两种方向 |
| `svg.mbt` | 渲染为自带交互脚本的 SVG（经典配色 + 悬停 / 缩放 / 搜索） |
| `hotspot.mbt` | 文本版 Top-N 热点报告 |
| `cli/` | 参数解析（独立成包，可脱离文件系统测试） |

**规模**：核心库约 956 行代码（其中 233 行是内嵌 JavaScript 字面量），
纯 MoonBit 逻辑约 723 行；另有测试约 1284 行，**122 个测试全部通过**。

### 4.3 可交互的产物

生成的 SVG 内嵌脚本，用浏览器直接打开即可：

- **悬停**：底部信息栏显示完整帧名、耗时与占比；
- **点击缩放**：以该帧为根展开，祖先帧变半透明、无关帧隐藏，`Reset Zoom` 复原；
- **`Ctrl-F` 正则搜索**：命中帧高亮，右下角实时显示命中占比；
- **`Ctrl-I`**：切换搜索是否区分大小写。

这些交互**已在无头浏览器中实测通过**（派发真实鼠标事件并校验 DOM 状态，14 项断言全绿）。

### 4.4 处理真实数据的工程细节

以下几点都是**被真实数据逼出来**的，不是凭空设计：

1. **限深必须合并而非丢弃。** 递归程序的栈可达数千层（实测最深 7254 层）。
   若把超出 `--max-depth` 的部分直接丢掉，深层耗时会被错算到最后一个可见帧上，结论完全失真。
   现在的做法是合并成一个 `(deeper)` 合成节点，把权重累加进去。

2. **「父矩形宽度 = 子矩形宽度之和」是一条硬不变量。** 靠两个合成帧维持：
   `(self)` 表示函数的自身耗时，`(deeper)` 接住被合并的深层帧。没有它们，图面上会出现空洞。
   这条不变量有专门的测试文件守护。

3. **确定性输出。** 同一份输入必须产出逐字节相同的 SVG，否则快照测试无从谈起。
   为此颜色使用自己实现的稳定哈希，而**不能用**标准库的字符串哈希（跨版本可能变化）。

4. **对上游「不完美」的兼容。** 真实数据里帧名形态混杂（已还原的 `a::b`、未还原的
   `pkg4name13func`、以及空帧名），解析层一律原样保留、不做猜测性修正。

### 4.5 一个有价值的实测发现

上游采样器的**采样密度取决于函数调用频率，而非运行时长**：

| 负载类型 | 时长 | 样本数 | 采样密度 |
| --- | --- | --- | --- |
| 调用密集（递归） | 91.89 ms | 55 | **599 样本/秒** |
| 循环密集（紧内循环） | 963 ms | ~40 | **42 样本/秒** |

相差 **14 倍**。且实测 `--iterations` 增加 10 倍，样本数只涨 1.6 倍——**延长运行时间并不能提高统计质量**。
这意味着循环密集型的程序（恰恰是最常见的一类热点）会被严重欠采样，短于约 25ms 的函数可能完全采不到。

这条结论已写入 README 的「已知限制」，因为**它直接影响使用者对图的解读**。

## 五、预期使用场景

1. **MoonBit 项目性能优化闭环**
   采样 → 转折叠栈 → 出图 → 定位热点 → 优化 → 再次出图与上一版对比。全程不修改被测程序。

2. **跨语言统一可视化**
   团队内 Python、JVM、C/C++ 项目各自采样后统一导出折叠栈，用同一个工具、同一种样式出图，
   避免为每种语言安装并学习一套独立的查看器。

3. **构建与 CI 流水线的阶段耗时分析**
   用轻量插桩记录各阶段耗时（如 `build;compile 1250`），出图后一眼看出瓶颈；
   SVG 可作为 CI 产物归档，便于对比历史版本。

4. **受限环境与文档场景下的离线出图**
   在内网、无 Go/Node 的机器上，或需要把性能图贴进 README、设计文档时，
   交出单个 SVG 即可，接收方无需安装任何工具。

## 六、技术亮点

| 亮点 | 具体做法 |
| --- | --- |
| **零依赖核心库** | 根包纯计算；IO 隔离在入口包，其余代码可在无文件系统环境复用 |
| **限深合并** | 超额部分合并为合成帧而非丢弃，避免深层耗时被错误归因 |
| **布局不变量** | 父宽严格等于子宽之和；最后一个子项直接取父右边界，消除数千个矩形后的浮点累积误差 |
| **消除亚像素裂缝** | 相邻矩形共用的边界量化到同一坐标，放大后不会出现白缝 |
| **确定性** | 自实现稳定名称哈希 + 排序口径固定，同输入必得逐字节相同输出 |
| **经典观感与合规并重** | 配色与交互行为对齐经典实现，但**不复制其源码**（许可证不兼容，见下节） |

## 七、已知限制（如实列出）

1. 上游采样**仅支持 wasm / wasm-gc** 目标，native CPU 采样不可用；
2. `moon-pprof` 需要 Rust 工具链（**仅采集端**）；核心库零依赖，只有命令行入口依赖官方包 `moonbitlang/x` 做文件读写；
3. 极深递归栈会被限深合并显示，无法在单张图上完整展开；
4. 采样分辨率受调用频率影响（见 4.5），短函数可能采不到；
5. 内嵌交互脚本只在直接打开 SVG 时执行——用 `<img>` 引用时浏览器不会运行 SVG 内的脚本，这是规范行为；
6. 帧的横轴按耗时降序排列（经典实现按名字字母序），属刻意的可读性取舍；
7. 差异模式只输出一个方向（以当前剖面为宽），因此「只在基线中出现」的帧不会显示。

### 8.2 关于 FlameGraph 的特别说明

`brendangregg/FlameGraph` 采用 **CDDL-1.0（弱 copyleft）**，与本项目的 Apache-2.0 **不兼容**。
因此本项目**只对齐功能规格**——即调色板的数值公式（`r=205+50v, g=230v, b=55v`）、
差异配色规则、以及交互的**行为语义**（悬停显示信息、点击缩放、Ctrl-F 搜索）——
所有 MoonBit 与 JavaScript 实现均为**独立编写**，其源码一行未被复制。

这一点在 README 与 `docs/DESIGN.md` §5b 中均有明确声明，以便审查。
